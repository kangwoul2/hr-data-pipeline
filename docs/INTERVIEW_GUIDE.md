# HR 데이터 파이프라인 면접 가이드

모든 답변은 **문제 → 원인 → 대안 → 선택 → 단점 → 검증** 순서로 설명합니다.

답변의 구현 범위는 [2026-09-17 검증 기록](VERIFICATION.md)을 기준으로 합니다. 기존 단위 테스트는 4개이며, PostgreSQL 재적재·롤백·HTTP API는 별도 환경에서 추가 검증했습니다. Airflow는 실제 ETL에 연결되지 않은 DAG 뼈대입니다.

## 1. 왜 노트북 분석을 별도 Python 코드로 옮겼나요?

노트북은 탐색과 시각화에는 좋지만 실행 순서와 현재 셀 상태에 의존하기 쉽습니다. 같은 입력에서 같은 결과를 반복해서 만들어야 하는 파이프라인에서는 명시적인 함수와 모듈 경계가 더 적합합니다. 그래서 기존 노트북은 분석 근거로 보존하고 실제 반복 실행 경로는 `quality → transform → storage → api`로 분리했습니다.

## 2. 왜 잘못된 행을 버리지 않고 전체 작업을 실패시키나요?

중복 직원 ID나 잘못된 이직 여부 값은 어느 행이 정답인지 시스템이 임의로 판단할 수 없습니다. 잘못된 행을 조용히 삭제하면 데이터는 줄었지만 작업은 성공한 것처럼 보일 수 있습니다. 현재 규모에서는 잘못된 원본을 명확하게 드러내기 위해 즉시 실패시키는 방식을 선택했습니다. 대규모 운영에서는 거절된 행을 별도 테이블에 보관하는 방식을 검토할 수 있습니다.

## 3. DB 제약조건이 있는데 애플리케이션 데이터 품질 검사가 왜 필요한가요?

책임이 다릅니다. 애플리케이션 검사는 적재 전에 입력 전체를 검사하고 오류 원인을 설명하기 좋습니다. DB 제약조건은 어떤 적재 경로가 들어오더라도 마지막 무결성 경계가 됩니다. 둘을 중복 기능이 아니라 서로 다른 방어선으로 사용합니다.

## 4. 왜 `to_sql(if_exists="replace")`를 사용하지 않았나요?

`replace`는 기존 테이블을 삭제하고 다시 만들 수 있기 때문에 기본키, 외래키, CHECK 제약조건을 잃을 수 있습니다. 그래서 스키마는 유지하고 하나의 트랜잭션 안에서 기존 데이터를 비운 뒤 새 데이터를 적재합니다. 중간에 실패하면 전체를 롤백해 일부 테이블만 새 데이터로 바뀌는 상태를 막습니다.

## 5. 왜 PostgreSQL을 선택했나요?

직원, 이직 여부, 부서 집계 사이의 관계가 명확하고 기본키·외래키·CHECK 제약조건과 트랜잭션이 중요합니다. 자유로운 문서 구조보다 관계형 무결성이 더 중요한 데이터라 PostgreSQL이 적합하다고 판단했습니다.

## 6. 왜 Airflow를 쓰고 Kafka는 사용하지 않았나요?

이 프로젝트의 입력은 실시간 이벤트가 아니라 전체를 다시 읽는 배치 CSV입니다. 그래서 실행 일정과 실패 관리를 확장하기 위해 Airflow DAG의 작업 순서를 정의했습니다. 다만 현재 태스크는 설명 문자열을 반환하며 실제 ETL 연결과 재시도 설정은 후속 과제입니다. 지금 실행 가능한 경로는 CLI입니다. Kafka가 필요한 실시간 이벤트 전달 요구는 현재 범위에 없습니다.

## 7. ETL 트랜잭션 범위는 어떻게 잡았나요?

파일 읽기와 데이터 변환 전체를 DB 트랜잭션 안에 넣지 않습니다. DB를 실제로 변경하는 구간만 하나의 트랜잭션으로 묶습니다. 오래 걸리는 파일 처리나 CPU 작업까지 트랜잭션에 포함하면 DB 연결과 락을 불필요하게 오래 점유할 수 있기 때문입니다.

## 8. 왜 부서별 집계 테이블을 미리 저장하나요?

API의 주요 조회가 부서별 집계이고 데이터 갱신이 배치 단위라면 매 요청마다 원본 행을 다시 그룹화할 필요가 없습니다. 배치 실행 때 집계를 미리 만들고 API는 그 결과를 조회하도록 했습니다. 실시간 갱신이 필요한 서비스라면 다른 방식을 검토해야 합니다.

## 9. 인덱스가 필요한지는 어떻게 판단하나요?

조회가 있다는 이유만으로 인덱스를 만들지 않습니다. 실제 조회 조건을 기준으로 `EXPLAIN ANALYZE`를 사용해 순차 탐색과 인덱스 탐색, 실행시간, 읽은 행 수를 비교합니다. 읽기 성능 이점과 쓰기 비용을 함께 봅니다.

## 10. 데이터가 매우 커지면 어떻게 바꾸겠나요?

현재 전체 재적재 방식을 그대로 키우지 않습니다. 먼저 변경분만 적재하는 방식과 임시 테이블을 검토합니다. 데이터 변환이 한 서버의 메모리를 넘는 수준이 되었을 때 분산 처리 엔진을 검토합니다. 기술을 먼저 정하지 않고 데이터 크기와 처리시간 요구를 확인한 뒤 선택합니다.

## 11. 무중단 갱신이 필요하면 어떻게 하나요?

현재는 하나의 트랜잭션으로 전체 데이터를 다시 적재합니다. 데이터가 커지면 임시 테이블에 새 데이터를 완성한 뒤 짧은 순간에 조회 대상을 교체하는 방식이나 버전별 스냅샷 방식을 검토할 수 있습니다. 목표는 조회 중인 사용자가 일부만 갱신된 상태를 보지 않게 하는 것입니다.

## 12. 이 프로젝트에서 가장 중요한 개선은 무엇인가요?

분석 알고리즘을 더 넣은 것이 아니라 **입력 데이터가 지켜야 할 규칙을 코드로 명시한 것**입니다. 입력이 잘못되면 작업이 실패하고, DB 제약조건을 유지한 채 적재하며, 같은 변환 로직을 자동 테스트에서 반복 검증할 수 있게 만든 것이 핵심입니다.

## 30초 답변

> 노트북 분석을 반복 실행 가능한 구조로 만들기 위해 입력 검사, 변환, 적재를 Python 모듈로 분리했습니다. 원본 1,470행을 직원·이직·부서 집계로 적재하고, 같은 입력으로 재실행한 결과가 동일한지 확인했습니다. 또 적재 중 오류를 주입해 세 테이블의 기존 데이터가 모두 보존되는지 검증했습니다. FastAPI 조회도 확인했으며 Airflow는 아직 DAG 뼈대 단계입니다. 분석 결과의 재현성과 실패 시 데이터 일관성을 직접 확인한 것이 핵심입니다.

## 13. 아직 해결하지 못한 문제는 무엇인가요?

빈 입력이 품질 검사를 통과하고, 변환에서 필요한 근속연수 두 열이 필수 열 검사에 포함되어 있지 않습니다. 따라서 입력 계약 보완을 우선하겠습니다. 이후 이번에 수행한 DB·API 검증을 CI에 포함하고 Airflow에서 실제 ETL을 호출하도록 연결하겠습니다. 실제 이직률 감소나 성능 개선율은 측정하지 않았으므로 성과로 제시하지 않습니다.
